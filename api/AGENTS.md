# Working on the API

Rules for `api/`, on top of the repo-wide rules in the root [`AGENTS.md`](../AGENTS.md). Read both before changing anything here.

`api/` is the server: Fastify 5 on Node 24, PostgreSQL through Drizzle ORM, migrations generated by drizzle-kit, Better Auth for accounts. Plain JavaScript (ES modules) with JSDoc, run directly with no build step.

## Commands

```bash
docker compose up -d db && npm test -w api                  # every test, each integration file on a fresh database
npm run test:unit -w api                                    # test/unit, which needs no database
npm run migration:generate -w api -- --name add-goals       # after changing a *.schema.js: writes the SQL migration
npm run migration:generate -w api -- --custom --name x      # an empty migration, for SQL the schema can't express
npm run migrate -w api                                      # apply pending migrations outside Docker
npm run seed -w api                                         # development data; idempotent, refuses to run in production
npm run dev -w api                                          # the API outside Docker, reading ../.env
```

The local stack mounts `api/src` and runs `node --watch-path=api/src`, so the API restarts when a source file changes. It watches the folder rather than each file, because a per-file watch misses a file an editor saves by replacing it (JUG-143). After a dependency changes, `docker compose up -d --build`. Every `up` runs the one-shot `migrate` service first, and the API starts only if it succeeds.

## How it fits together

- **Layers.** Routes map URLs to controllers, controllers speak HTTP, services hold the business logic and the queries. A domain may skip a layer it doesn't need.
- **Factories with explicit dependencies.** Services are `createXService({ db })`, controllers `createXController({ ...services })`, and route plugins take their controller as an option. Only `app.js` creates and passes them, which is what lets tests build the whole app on a scratch database.
- **Configuration is read only in `config.js`.** A missing or malformed setting stops the process at startup with a message saying what to set. A new setting goes in `config.js`, in `.env.example`, and in what `docker-compose.yml` passes to the `api` service.
- **The `/api` prefix is stripped by Caddy** before the request arrives. Register routes without it: `/me` here is `/api/me` to the browser. `auth/auth.routes.js` puts it back for Better Auth, which routes on its full base path.
- **Every route has a response schema,** and the schema is also the allowlist of what leaves the server, since fields not listed are never serialized. That is how private data stays in. A route that answers a 4xx or 5xx with a body declares that status too, with `errorBody` from `http/schemas.js`.
- **Errors have one shape**, `{ error, code? }`, from `handleError` in `app.js`. Throw one of the classes in `errors.js` for a client's own mistake, and its message and code are sent back. Anything else becomes a logged 500 saying "internal error", so internals are never described — including `UpstreamError` (502), which puts a provider's failure in the log and not in front of the parent. The one 5xx sent as thrown is `UnavailableError` (503), which says a feature this server wasn't configured for is off, such as voice notes with no speech-to-text service; its code is how the web tells that from a failure.
- **Access is one route option.** `config: { access }` is `'public'`, `'session'`, or `'family'`. A route that says nothing gets `'session'`, so a new route is closed until it says otherwise. One `preHandler` in `app.js` runs `requireSession` (401, puts the adult on `request.session`) and then `requireFamily` (409 until the adult has saved a family, puts it on `request.familyId`). Controllers read both through `userOf(request)` and `familyOf(request)`. Only health, Better Auth's routes, and the admin are public; make a route public only when it truly must be.
- **Queries go through Drizzle** on the `db` from `db/client.js`: the query builder for most things, `db.query` to load a row with its relations, and the `sql` template for what is Postgres-specific. **Values are always parameters:** never build SQL from strings, never put input in `sql.raw`. Columns are camelCase in code and snake_case in the database. Writes that must succeed or fail together go through `db.transaction`.
- **A failed query throws `DrizzleQueryError`,** whose message includes the query's parameters, which can be a family's names. The Postgres error is its `cause`, and that is what `handleError` logs.

### Families and the catalog

- **Each adult has one family** for now; the second parent joins in 0.6. The profile holds the parents, kids, pets, toys, and the home, and each kid holds their own interests (`kid_interests`, JUG-144). A `Profile`'s own `interests` are derived, never stored: the interests of the kids in it, each once, so `playingProfile` carries only what the kids playing love.
- **The profile knows toys only by name.** Saving it changes a toy's name and order and nothing else, so a client that sends toys must send each toy's id. `PUT /family` leaves the toys alone when it gets none, which is how Mi familia saves, since its form has no toys (JUG-21). The rest of what is known about a toy lives in `toys/` (JUG-18).
- **Parents, the pet's animal, and the home** (JUG-21). `parents` are a name and what the kids call them (`calledAs`, "Mamá" when a save leaves it out); none of them needs an account. A pet's `kind` and the family's `home` are keys from `families/kinds.js`, a dog and null until the family says. `PUT /family` leaves the parents and the home alone when it gets none. Nothing reads the home yet.
- **Household materials are a list in code** (JUG-153). `materials/materials.js` holds the categories and each material's key, label, and `common` default. `household_materials` keeps only the family's answers, so a material with no row is at its default: on for what almost every home has. **Never change a key** once families may have answered it. A template's `materials` are keys from that list, the ones it can't be played without; the catalog refuses any other, and `suggest` skips a template that needs a material the family doesn't have. Something every home has, like a plate, isn't on the list.
- **Suggestions are ranked, not drawn** (JUG-104). `activities/ranking.js` is pure: given the templates that fit (age, slots, materials, as before), it scores each and returns them best first. The score is four factors multiplied: **fit** (a bonus for a template whose `themes` match what the kids playing love, one that names an interest, and one that drew a favorite toy), **feedback** (one Thompson-sampling draw from Beta(ups, downs), counting this family's reactions in full, other families' at a fraction, and reactions to similar templates by their Jaccard similarity over the tags), **freshness** (a template seen lately waits, on an exponential curve, longer when they said they played it; and once any discovery game is offered, every one of them waits, so more sound sets don't mean more screen), **difference** (for *Otro juego*, what is like the juego being left loses by its similarity), and **moment** (JUG-26: a calm moment keeps the low-energy templates whole and takes most of the high-energy ones away, a lively one does the reverse, and no moment leaves every template where it is). A template this family gave a thumbs down to, and the juego being left, are out unless nothing else fits. `DEFAULT_WEIGHTS` is the one place the numbers live, and the winner's score parts and weights are saved on the activity as its `pick`, so a suggestion can be read back. The ranking is deterministic for a seeded `random` and a fixed `now`, and each rule has a unit test.
- **Every template has a rating** (JUG-192), where every family's feedback starts: `rating`, 1 to 5, 3 unless the admin changes it. `priorOf` turns it into the ups and downs the Beta starts with: two `prior`s split at half and half for a 3, and `DEFAULT_WEIGHTS.rating` more or less for each step, so among twenty juegos alike a 5 comes first about five times as often as a 3, and a 1 about a tenth as often. Other families' reactions move it from there at `others` each, which is how what families like comes up more for everyone. The admin sends each template with `reactions`: every family's ups and downs, and the rating now (`ratingNow`), on the same scale, from `activities.ratings()`. **No parent ever sees a rating.**
- **The weather picks between inside and outside** (JUG-25). Every template already says which it is (`place`), so the ranking's weather factor is a lookup: a `fine` afternoon halves every indoor template, so the few outdoor ones come up; `poor` weather takes most of the outdoor ones away; `fair` changes nothing. `weather/conditions.js` is the pure rule that reads a forecast into those three, over now and the next few hours, and `LIMITS` is the one place its thresholds live. **The weather never fails a juego:** a family that hasn't said where they live, a provider that is down, and a request that runs long all answer null, and the ranking is then exactly what it was before the weather existed.
  - **The family says where they live in their own words** (`families.location`), and the geocoder in `places/` turns them into coordinates when they are saved, never inside the transaction. A city or a zone is all this is for — the weather over Buenos Aires is the same in every barrio — so the coordinates are a city's and never a home's, and nothing ever asks the device where it is. Words nobody can place are still saved, with no coordinates. `asKnown` maps what Argentines call their city onto the name the geocoder knows ("Capital Federal" and "CABA" are both Buenos Aires to GeoNames, which has neither).
  - **Where a family lives is theirs.** The words and the coordinates never go into a log or an error message, which is why both clients say only what kind of failure it was and never the URL they called. `GET /family` answers with the words and whether they were found, never the coordinates: the response schema is the allowlist that keeps them in.
  - **Cached per location on the server,** keyed by the coordinates rounded to about a kilometre, so one call covers a city and nothing about which family asked is kept. `WEATHER_CACHE_MINUTES` sets how long. Open-Meteo needs no account and no key, so a fresh checkout has the weather with no setting at all.
  - **No test reaches either service:** `startApi()` builds the app with no forecaster and no geocoder unless the test passes its own.
  - **Night keeps the juego at home** (JUG-191). `nightAt()` in `clock.js` is night from 19:00, from 18:00 in June, July, and August, until 07:00, and the ranking reads it as `poor` weather whatever the forecast, with or without a place. The pick keeps `night` beside `conditions`.
  - **Home shows what the ranking reads** (JUG-191). `GET /activities/weather` answers `{ weather, reason, night }` from `activities.outside()`, which reads the place, the cache, and the clock the way `suggest` does, so the line on Home is what the ranking does. It answers `null` when there is no weather, and never a temperature or a place.
- **Themes are a list in code** (`catalog/themes.js`), like the materials. A template's `themes` say what it is about, by key; the catalog refuses any other, and the admin picks them from `GET /admin/themes`. `themesOf` reads a family's interests, as typed, into keys by word stems with accents and case ignored, so "los dinosaurios" and "Dinos" both reach `dinosaurios`. Keep a stem long enough not to catch other words, or end it with `$` for a whole word only. Never change a key once templates carry it.
- **The moment a juego is for** (JUG-26). `clock.js` holds the one rule the whole API reads: calm from 19:00 to 07:00 in Buenos Aires, the window night mode uses, and lively the rest of the day. A story follows it (JUG-139) and so does `POST /activities/suggestions`, whose `mood` is `calm`, `lively`, or `null` for no preference. **Left out, the clock decides,** so a client that says nothing still gets a calm juego before bed; the web sends what the parent sees, since its own clock is the one on the screen. The moment only lowers a score, never to zero, so a family whose fitting templates are all energetic still gets one at night. The child's own routine arrives with the fuller data model and replaces the clock.
- **The feedback tap** (JUG-23) is `reaction` on the activity row: `up`, `down`, or null, set by `PUT /activities/:id/reaction`, one per juego and changeable. It saves the reaction and when, and nothing about how long they played. Every ranking reads every family's reactions, so a reaction is the one thing a family gives that reaches the others.
- **The history** (JUG-188). `GET /history` answers with the juegos the family played and the stories they read in the last 30 days, each once, at the last time it was played or read, latest first. `history/` holds only the window; each list comes from its own service. A juego is played from its *Empezar*, which the web sends as `POST /activities/:id/plays` and which sets `played_at` again each time, or from a thumbs up, so juegos from before this and ones started offline count; it is dated by the later of the two. A story's `read_at` is set when it is written and again by `POST /stories/:id/reads` each time it is opened. Neither keeps how long anyone played or read. `GET /activities/:id` sends one juego as the parent saw it, so one from the history opens on a device that never had it. `GET /stories`, the shelf on ¿Cuál leemos hoy?, is the two stories read last (JUG-189).
- **Discovery games** (JUG-128). A template whose `game` is set is a game, and *Empezar* opens it instead of the timer. The one game so far is ¿Qué suena? (JUG-177), `{ type: 'sounds', set }`: `games/sounds.js` holds the sound sets in code, like the materials, and the catalog refuses a set that isn't on it. Each item has its name as the options read it, with its article; a `group` of items that sound close; the stems a toy's words are matched against; and, for the dog and the cat, the pet kind whose name it takes.
  - **The game is dealt when its juego is suggested,** and saved on the activity as `game`, so the parent plays what the screen showed, offline too. `games/rounds.js` is pure: five sounds from the set, each with its options. The youngest kid playing decides how many and how close: three that sound nothing alike under 3, three from 3 with one close, four from 5 as close as the set has. An option is the pet's name for its animal, and a toy's family name for what the toy is, read from its name, other names, and description; a toy that names more than one item names none.
  - **The recordings are files, not rows:** `api/sounds/<set>/<key>.mp3`, served to a signed-in adult by `GET /sounds/:set/:file`, which reads only a file named by an item on the list. The API image copies the folder, and the dev stack mounts it. `api/sounds/credits.json` says where each one came from and under what license; a round carries its `credit` only when the license asks for one, and the web shows it. CC0 comes first; CC-BY and NonCommercial are fine, since Ludi is not sold (JUG-178), and NoDerivatives never is, since every clip is trimmed. `test/unit/sound-rounds.test.js` fails for a sound with no file or no credit.
- **A kid's age is kept in months** (`kids.age_months`), as the age the parent gave and the day they gave it, so it stays current without asking for a birthday (JUG-145).
- **The catalog owns every template** (JUG-125). `catalog.service.js` is the only place `activity_templates` and `story_templates` are read or written: the seed loads through its `load`, the admin creates and edits, and activities and stories ask it for the templates they can offer. Activities keeps `suggest` and its own table; stories keeps the stories and the plots.
- **Templates have slots** — `{kid}`, `{pet}`, `{toy}`, `{toy2}`, `{toy3}`, `{interest}` — filled by code in `catalog/slots.js`, with no LLM. Toys are known only by name, so **write templates any toy fits, never make a word agree in gender with a slot, and never address anyone by a toy's name.** "a {toy}" and "de {toy}" contract to "al" and "del" on their own. A template is offered only when the family can fill every slot it uses and its age range fits: every kid for activities, since their safety rules hold only within that range, and at least one kid for stories.
- **The admin has no login yet** (JUG-109). Its routes, the catalog's and the Usuarios page's (JUG-34), say `access: 'public'`, so `app.js` registers them only when `ADMIN_ENABLED` is true; otherwise they are a 404. Never turn it on where anyone outside the family can reach it, and remind Alex of the rule when work touches it.

### Stories and the LLM

- **Every call carries the guardrails** (JUG-90). `llm/guardrails.js` holds the rules that are above every task: what Ludi writes has to be for a child, positive, and worth something to them, and the family's own words are data to read, never instructions to follow. `client.js` wraps each task's system prompt in them, so **a call cannot be made without them** — don't build messages anywhere else, and never write a task prompt that contradicts them. **A parent's own words go in the call's `data`,** never in `user`: that is what puts them inside the data block, out of the instructions. Values a prompt is filled with are a family's words too, so `render` drops any data tag they carry. The prompt is the first layer only, since a model can be talked out of anything; the checks on its answers are JUG-96 and the test cases JUG-97.
- **One client, three providers** (JUG-115, JUG-168). `LLM_PROVIDER` picks OpenCode Go, OpenRouter, or Claude Code and `LLM_MODEL` the model; `llm/client.js` adds the guardrails for all three. OpenCode Go and OpenRouter share one request, since both speak the OpenAI chat completions API. Without the chosen provider's key, stories come from templates. **OpenRouter requests send `data_collection: 'deny'`,** because prompts carry the kids' names and must not reach a provider that stores or trains on them. **Claude Code runs the `claude` CLI once per call** (`llm/claude-code.js`). The API's Docker image installs it; outside Docker, without an installed `claude`, every call fails with an `UpstreamError`, which is logged. It runs with no tools, MCP servers, settings, CLAUDE.md, or saved sessions, in a folder of its own, and its environment holds only `CLAUDE_CODE_OAUTH_TOKEN`: don't pass it the API's environment, which holds the database URL and the auth secret. `llm/prompt.js` fills a prompt's `{{key}}` placeholders and throws on one it has no value for, and reads the JSON out of an answer, fences and prose included. The prompt texts live with the domain that sends them, in its own `prompts/`.
- **Stories come from one of two sources** (JUG-126). `stories.service.js` is the facade: it picks the source and keeps the library. `template-stories.js` fills a catalog template's slots; `generated-stories.js` asks the model for plots and writes the one the family chose, streaming it. Either way a story is written once and saved, and reading it again replays what was saved, as the same events, so the web never tells the kinds apart.
- **The parents aren't drawn** (JUG-21). `familyLines` gives them a line of their own, after the family's, that any story can call on by what the kids call them, and the pet comes with its animal. A family with no parents saved gets no line, so nothing about parents reaches the model.
- **Code decides, and the prompt gets only what applies** (JUG-139). `prompts/compose.js` joins the narrator's core, one of the eight age-band fragments, and one of the two moment fragments. The band is the youngest kid playing with a known age, the moment is the Buenos Aires clock, and the weather joins as a third fragment in 0.3. **No band or moment a story isn't for is ever sent.**
- **The bands are six months wide under four years** (JUG-145): `1`, `1.5`, `2`, `2.5`, `3`, `3.5`, then `4` and `5`. Each band asks for more than the kid can say: a story slightly hard to follow beats one that is too simple, and the narrator's core says so.
- **The casting is drawn before the model is asked** (JUG-139), except for a story the parent asked for by voice, whose casting is the request's (JUG-156). `casting.js` is pure: given the playing profile, the weights, a random function, and the last five castings, it draws a screen of two (JUG-157). The first is the classic (`cast`): the anchor kid leads, and a family interest is the theme when its draw says so. The second is new (`wildcard`): it has no family theme, and the model is asked for a place, a character, or a situation the family hasn't heard. Whether the kids playing are in it is drawn, and so is whether one of them leads; otherwise the pet or toy that came in, or a character the model invents, leads, so the kid doesn't star in every story (JUG-161). In both, whether the pet and a toy are in is drawn, and the two never share a toy while there are more. The options prompt tells the model that each plot names only its own cast, since the family lines above the castings list everyone drawn into either. A keyword story is cast as the classic with its keyword as the theme (JUG-157). `DEFAULT_WEIGHTS` is the one place the probabilities live, and the draw takes them as an argument so per-family weights can come later. The random numbers and the weights are saved with the plot, the story, and the audit, so a draw can be read back.
- **The options are one call, read as it streams** (JUG-139). `options()` draws the two castings and hands them to one model call, and `OptionsParser` pulls each plot out as its braces close, so a plot is sent on while the model writes the next. One call keeps the system prompt from being paid for twice, which is why `GET /stories/options` is a stream like `POST /stories/write`. Plots stay pickable for 7 days, since each device keeps the options it was shown, and asking for options deletes the family's plots older than that. An answer with no readable plot is asked once more, then it is an `UpstreamError`. On OpenRouter a reasoning model is asked to skip its thinking, without which the answer is all thought and no plots.
- **A keyword is a story with no plot** (JUG-140). `POST /stories/write` takes `{ keyword }` instead of `{ id }`, and it has to be one of the interests of the kids playing, as typed, or it is a 400. Only the model writes these, so a server without one answers 503. The model invents the plot and opens with a `TÍTULO:` line, which `StoryParser` hands back so the stream can send a `title` event before the first paragraph. Every tap writes a new story; nothing is deduplicated.
- **Sounds to act out** (JUG-170). Every story and episode prompt asks for a `SONIDOS:` line before `PARTE 1`, with one to three sounds as `sound | who | how`, and the narrator's core asks for each sound to be marked between brackets in the text. `StoryParser` keeps the line out of the story wherever it lands and tidies each paragraph with `tidyMarks`, so only a marked sound keeps its brackets; titles, teasers and the other fields lose theirs. `tellStory` sends a `sounds` event just before the first paragraph, and a line that comes later is dropped, so the legend never changes while the parent reads. The legend is saved in `stories.sounds` and replayed before the paragraphs; template stories have none. The audit's `written` row counts the sounds listed and the marks in the text.
- **A story asked for in the parent's words** (JUG-156). `POST /stories/understanding` reads a voice note's words into a request — `summary`, `family`, `characters`, `setting`, `theme`, `plot` — and saves nothing; words that ask for no story come back with an empty `summary`. `POST /stories/write` takes that request back as `{ request }` once the parent says yes. `requests.js` holds it to the same rules both times: a name is family only when it is one of the family's, spelled as they spell it, and anything else is a character. The story is written for the kids the request names, or the kids playing when it names none; `castRequest` makes the casting from it with no draw, and the request goes to the model as `data`, so the story prompt treats it as material and the band, the moment, and the guardrails still win. The teaser is the request's summary. Only the model reads and writes these, so without one both answer 503, and **neither the words nor the request go into a log or an error message.**
- **A series is a story kept going** (JUG-59). `series.js` owns `story_series`; episodes are rows in `stories` with `series_id` and `episode`. `POST /stories/:id/series` turns a read story into episode 1 with no model call, taking its casting and its storyline (the plot's premise, or the teaser), which no episode changes. `POST /series/:id/episodes` streams the next one like any story. The second episode is written from the whole first one, and the same answer names the series (`SERIE:`), says where it happens (`LUGAR:`) and sums up episode 1 (`ANTES:`); every later one is written from the series' storyline, setting, characters, and each episode's `RESUMEN:`. `PERSONAJES:` adds the characters the model invented. `StoryParser` keeps all those lines out of the story. The episode number is settled when it saves, under a lock on the series, so two written at once are both kept. `STORY_SERIES_EPISODES` caps a series (10 unless set), and a full one answers 409. Removing a series sets `removed_at`: it shows up nowhere and its episodes return to `GET /stories`. Only the model writes episodes, so without one starting a series answers 503.
- **The story audit** (JUG-139) is `story_audit`: one row per option offered, one when a plot is picked, one when its story is saved. It holds no prompt text and no story text, and names the kids only by id. Nothing serves it over HTTP; it is read in SQL. **A failed audit insert is logged and let go,** since a story must never fail because its record didn't save.
- **A family from the parent's own words** (JUG-11). `POST /family/understanding` returns a profile for the parent to confirm and saves nothing. It keeps each name spelled as the parent wrote it and flags a parent, kid, or pet the text doesn't name. A parent's `calledAs` and a pet's `kind` are null when the text doesn't say (JUG-21), so a note about what changed doesn't overwrite them; the web fills in the defaults before saving. Each interest goes on the kid the text gives it to; what the text ties to nobody goes on every kid (JUG-144). **The text never goes into a log, and the model's answer can repeat it, so neither goes into an error message.** It is stored only in `audit_transcripts`, only while `AUDIT_TRANSCRIPTS` is on (JUG-116). `/me` returns `familyFromText`, false without an LLM, so the web starts first run at the form.
- **Voice notes never keep audio** (JUG-95). `POST /voice/transcribe` takes the recording as the raw body with an `audio/*` Content-Type, read into one in-memory buffer of 8 MB at most by a parser registered only inside the voice plugin. `voice/transcriber.js` speaks the OpenAI transcriptions API, so `STT_URL`, `STT_MODEL`, and `STT_API_KEY` choose the service. **Never write the audio to disk, log it, or put it in an error message, and never log the words that come back.** Without `STT_URL` the route answers 503. Tests pass their own `transcriber` to `startApi()`.

## Accounts and the guardrails

- **Better Auth** handles sign-up, sign-in, sign-out, and sessions under `/auth/*`, with email and password, and with Google. The session is an httpOnly cookie that lasts 30 days and is renewed with use, so a parent who opens the app once a month stays signed in.
- **An invitation is the only way to create an account** (JUG-34), whatever the sign-in method: the `user.create.before` hook in `auth/auth.js` admits a sign-up only for an email holding an open invitation, and only when the invitation's own token comes with it. There is no allowlist and no other door. **This is how "no outside testers until the guardrails are complete" is enforced. Never loosen it, and remind Alex of the rule whenever work touches sign-ups.**
- **Invitations** live in `invitations/`. The admin's `POST /admin/invitations` sends the email a link to the web's `/invitacion` with a random token and the email, and keeps only the token's SHA-256. Inviting the same email again replaces the token, and an email that has an account is refused (409). A link works for 14 days.
  - **With no mailer the link comes back in the answer** instead of going out, which is how the first account on a new machine gets in; when an email is sent, the answer's `link` is null, so a token never travels further than it has to. `open()` writes an invitation and hands back its link without sending anything, which is what the seed uses.
  - **The token has to come with the sign-up,** or the invitation doesn't count: `invitation` in the body of `POST /auth/sign-up/email`, or `additionalData.invitation` on `POST /auth/sign-in/social`, which Better Auth keeps in the OAuth state until Google's callback. The hook admits the sign-up only when the token is open and its email is the one signing up, marks that email verified, and marks the invitation accepted once the account exists. A Google account with another email is refused with `INVITATION_OTHER_EMAIL`.
  - **`POST /invitations/check`** is public: the landing screen sends the link's token and email, in the body so neither reaches a request log, and learns whether the email already has an account. Expired links answer `INVITATION_EXPIRED` unless it does.
  - **Never log an address or a token.**
- **Sign in with Google** (JUG-63) is on when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set; without them `POST /auth/sign-in/social` answers 404 with `PROVIDER_NOT_FOUND`.
  - **It asks Google only for what signing in needs:** the `openid`, `email`, and `profile` scopes, with no offline access, and it keeps the name and email but not the picture. Never add a scope.
  - **A new Google account passes the same check** as an email sign-up. Refused, the browser goes back to the web's `errorCallbackURL` with `?error=SIGNUP_NOT_ALLOWED`, and no user is created.
  - **It links to an existing account with the same email** when Google says the email is verified. The account it links to doesn't need a verified email (`requireLocalEmailVerified: false`), since only invitations verify an email so far.
  - **Google returns to `BETTER_AUTH_URL`** + `/api/auth/callback/google`, the redirect URI registered with Google, so Google sign-in works only from that origin, not from `TRUSTED_ORIGINS`. Google refuses `ludi.local`; the [README](../README.md#sign-in-with-google) says how to try it locally.
  - **Tests stand in for Google** by replacing `fetch` for its token endpoint, in `test/google.test.js`.
- **Better Auth checks the origin** of sign-in and sign-up, accepting `BETTER_AUTH_URL` and the origins in `TRUSTED_ORIGINS`. That decides where the app can be opened from, not who can sign up.
- **Every email is the same branded message** (JUG-34). `email/message.js` takes a preheader, a heading, paragraphs, one button, and a closing line, and gives back the HTML and the plain text, built from the same words so they can't drift. It escapes everything: a family's own words can never become markup, and only an `http` or `https` link reaches the button. A part left out is a failure that names the part, never the words. An email lives with the domain that sends it, like `invitations/invitation-email.js`, and calls `renderMessage`; no domain builds HTML of its own.
  - **The HTML is compiled from MJML and committed.** `email/templates/message.mjml` and the partials in `templates/partials/` hold the brand: the wordmark with its ronda, the card, the button, the footer. `npm run email:build -w api` writes `message.html` beside it, which is what the API sends, so **commit the `.mjml` and the `.html` together**; `test/unit/email-message.test.js` fails when they differ. MJML is a dev dependency and the production image installs none, the way the app icon's PNGs are rendered and committed. `npm run email:preview -w api` prints an email to look at in a browser.
  - **The brand's colours are written out as hex** in `templates/partials/head.mjml`, because an email can't read `tokens.css`: when a brand colour changes, that file changes with it. No web fonts and no images, so opening an email fetches nothing and nothing can track the open.
- **Email goes through one mailer** (JUG-169). `email/mailer.js` sends through any SMTP service, chosen by `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, and `EMAIL_FROM`; Resend to start. Without `SMTP_HOST`, `createMailer` returns null. Ports 465 and 2465 use TLS from the start and every other port must upgrade with STARTTLS, so nothing goes out in plain text. The droplet uses 2465, since DigitalOcean blocks 25, 465, and 587. **Never log an address or a message, and never put either in an error message:** a failure becomes an `UpstreamError` with nodemailer's codes only. Invitations are the only email sent so far; `npm run email:test -w api -- you@example.com` sends one, with a link that leads nowhere, to check the settings, the domain's DNS records, and how the template looks in a real inbox.
- **The admin removes an account** (JUG-175). `DELETE /admin/users/:id`, in `accounts/`, deletes the user and the family it belongs to, so the cascades take the sessions, the sign-in methods, the audit rows, and everything under the family. Each adult has one family for now, so the family goes with its only member; when the second parent arrives (0.6) this has to leave a family that still has one. Afterwards the email can be invited again. It answers 204, or 404 with `ACCOUNT_NOT_FOUND`. Like the rest of the admin it is public, so it exists only where `ADMIN_ENABLED` is true.
- **Better Auth's tables are ours,** defined in `auth/auth.schema.js` with plural names like every table. An upgrade or plugin that needs new columns adds them there and generates a migration.

## Migrations and seeds

- **The schema is code.** Each domain defines its tables in `<domain>.schema.js`, and `db/schema.js` gathers them; a new schema file goes there too. Change the schema, then `npm run migration:generate`. **Read the SQL before committing it,** since a renamed column can come out as a drop and an add. For what the schema can't express, such as moving data, `--custom` writes an empty migration to fill in. Commit only the new `.sql` file.
- **Migrations only go forward.** To undo one that has run anywhere, generate another. Never edit a migration that has run, and never create tables from application code.
- **Generate on top of main.** Drizzle applies only the migrations newer than the latest applied, so one from a branch that main has moved past would be skipped and the runner stops instead. If main gains a migration while your branch has one, delete yours, merge main, and generate again. On a fresh clone (no `migrations/meta/`), run `drizzle-kit push` first to populate the baseline.
- **Data comes from seeds,** never from application code or the web, and never as a placeholder record or a side effect that exists only to have data.
  - **Catalog templates** are in `seeds/catalog/` and load on every `docker compose up`. A template already in the database is never overwritten: the database is the catalog's home (JUG-9). Once loaded, a template changes in the admin, and one deleted there keeps its row so the seed never brings it back.
  - **Demo accounts** are in `seeds/development.js`, loaded through Better Auth and the services the way the app does, skipping whatever exists. Each one opens its own invitation first, since that is the only way to create an account, and nothing is emailed. Their passwords are in the repo, so they never run anywhere real. Add a family setup there, and to the [README](../README.md)'s table, when exploring the app needs one.

## Tests

- **Two kinds**, both with `node:test` and `node:assert/strict`: integration tests in `test/<domain>.test.js`, which build the app on a database, and unit tests in `test/unit/<name>.test.js` for a module that is pure or speaks only to a fake server of its own. A file that mixes the two is split in two.
- **The integration tests need a Postgres** they can create databases in: `docker compose up -d db`, or set `TEST_DATABASE_URL`.
- **`startApi()`** in `test/helpers.js` creates a fresh database, applies every migration, and builds the app on it; `close()` drops it. Each file starts its own in `before` and closes it in `after`. `api.db` is the Drizzle client to build services with, `api.pool` the pool under it for checking rows in plain SQL, and `testConfig(overrides)` the config it builds on.
- **Requests go through `app.inject()`,** with no network. `cookiesFrom(response)` carries a session to the next request.
- **Cover every new endpoint,** including what it must refuse: no session, someone else's data, invalid input.

## Adding an endpoint

1. Put the queries and logic in a service in `src/<domain>/`, and the HTTP handling in a controller beside it.
2. Add the route in `<domain>.routes.js`, with a response schema for every status that returns a body. Pick its access: leave it out for a route about the signed-in adult alone, `access: 'family'` for one that reads or writes the family's data, and `access: 'public'` only for a route that must answer without a session at all.
3. Wire the service, controller, and routes in `app.js`.
4. If the schema changes, change the domain's `<domain>.schema.js` and generate a migration. If exploring the app needs data, add it to the seeds.
5. Write the integration tests.
6. Call it from the web as [`web/AGENTS.md`](../web/AGENTS.md) describes.
